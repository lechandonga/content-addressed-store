# 内容标识与校验规则

## 1. 内容地址

所有数据（分块与清单）统一使用形如 `sha256-<64 位十六进制>` 的内容地址：

```
sha256-3f1b...e9
```

- 算法前缀使将来可以平滑引入新哈希算法；
- `cas.ParseAddr` 校验前缀与十六进制长度，非法地址一律拒绝；
- `cas.AddressBytes(data)` 计算字节地址。

## 2. 分块与清单（Manifest）

写入内容时按配置的 `ChunkSize`（默认 1 MiB）定长切分；空内容产生一个零长度分块。

```
Manifest (JSON, v1)
├── version: 1
├── size:    <整条内容总字节数>
└── chunks: [
      { "addr": "sha256-...", "size": 1048576 },
      ...
    ]
```

- 每个分块地址 = 该分块原始字节的 SHA-256；
- **内容标识 CID = 清单规范序列化字节的 SHA-256**。因此：
  - 任一分块被篡改 ⇒ 该分块地址对不上，读取失败；
  - 清单中任何字段（分块顺序、大小、数量）被篡改 ⇒ 清单字节哈希对不上 CID，读取失败。
- 清单 JSON 由 Go `encoding/json` 按结构体字段顺序确定性输出，相同内容始终得到相同 CID。

## 3. 读取时的完整校验链

`Get(ctx, cid)` 严格按以下顺序校验，任何一步失败都不会返回拼接结果：

1. 取清单字节（本地或对端），要求 `AddressBytes(raw) == cid`，并解析、校验：
   - `version == 1`、`size >= 0`、至少一个分块；
   - 每个分块地址合法、大小非负；
   - 各分块大小之和必须等于 `size`。
2. 按清单顺序逐块取字节，要求 `AddressBytes(block) == chunk.addr`，
   且实际长度等于清单声明长度。
3. 拼接后再次核对总长度等于清单 `size`。

对端返回的字节同样在本地重新哈希；对端给错内容（恶意或自身损坏）会被判为
`ErrCorruptChunk/ErrCorruptManifest`，客户端自动回退到下一个对端。

## 4. 可区分的失败原因

读取失败时返回的 `*cas.Error.Kind` 精确定位问题层级：

| Kind | 触发条件 |
| --- | --- |
| `not_found` | CID（清单）在本地与所有对端都不存在 |
| `missing_chunk` | 清单存在，但某个分块在本地与所有对端都不存在 |
| `corrupt_chunk` | 分块字节哈希与其地址不一致（本地静默损坏或对端给错） |
| `corrupt_manifest` | 清单字节哈希与 CID 不一致、JSON 非法或内部引用不一致 |
| `capacity` | 对象/响应过大，或容量回收后仍无法容纳 |

设计要点：**损坏与缺失不会互相掩盖**。例如本地分块损坏且未配置对端时，
错误始终是 `corrupt_chunk`，而不会因为损坏文件被隔离后变成 `missing_chunk`。

## 5. 损坏数据的处置：隔离而非删除

校验失败的本地文件会被原子移动到 `quarantine/` 目录（加时间戳与随机后缀）：

- 损坏字节立即离开其内容地址，绝不会再被返回；
- 保留原始文件用于事后取证，可按 `QuarantineTTL` 配置保留时长（`<0` 永久）；
- 下次访问该内容时从对端重新获取正确版本。

## 6. 去重

- 内容寻址天然去重：相同字节 ⇒ 相同地址 ⇒ 同一路径。
- `Put` 先查清单是否存在；存在即整体复用。
- 写入分块时逐块“存在即复用”：与历史内容共享的相同分块不会重复落盘。
- 并发 `Put` 同一内容由 `commitMu` + `commitIfAbsent` 串行去重提交，
  只产生一份文件，绝不会相互覆盖。
