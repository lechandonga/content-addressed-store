# 保留与回收策略

## 1. 引用（Pin）是保留的唯一依据

- `Pin(ctx, name, cid)` 创建命名引用；被任一引用指向的内容（清单及其全部分块）
  在任何回收路径下都**不会被删除**。
- `Unpin(name)` 删除引用；删除后内容不会立刻消失，而是在下次容量回收时按 LRU 处理。
- 同一名字重复 Pin 同一内容是幂等的；指向不同内容返回 `ErrRefConflict`。
- Pin 本地缺失的内容时，会像 `Get` 一样从对端按需获取并完整校验。

## 2. 分块引用计数与去重删除

回收采用 mark-sweep：

1. **标记**：以 `refs/` 中的引用为根，解析其清单，汇总所有被引用的分块。
2. 每个分块维护“被多少现存合法清单引用”的计数。
3. 驱逐一条无引用内容时，仅删除其清单；随后的分块清扫只删除**引用计数归零**的分块。
   因此被多个内容共享的去重分块，只要还有一个内容（含被引用内容）使用，就不会被误删。
4. 不属于任何现存清单的哈希正确分块，作为孤儿安全删除（回收用量并保持磁盘整洁）。

## 3. 容量水位与 LRU

当配置了 `MaxBytes > 0`：

- `HighWatermark`（默认 0.90）：已用量超过该比例时，下一次 `Put/Get` 容量预评估
  或手动 `Collect` 会触发回收。
- `LowWatermark`（默认 0.70）：回收尽量把用量降到该比例以下。
- 无引用内容按清单的**最近访问时间**（`Get`/`Put` 命中会 touch）从旧到新驱逐，
  直到腾出目标字节数；`EvictAll` 可驱逐全部无引用内容（被引用者仍保留）。
- 回收后仍无法满足容量时，写/获取返回明确的 `ErrCapacity`：
  - 普通 `Get` 超出容量：先尽力回收，仍放不下才失败（内容仍可在对端保留）；
  - `Pin` 触发的获取语义是“获取即保留”，不允许通过驱逐来腾位，放不下直接失败。

`Put` 在容量不足时会自动先执行一次 `Collect(MakeRoom=需要字节数)` 再重试，
因此容量压力下对外仍保持“写入或得到明确容量错误”的一致行为，不会写超额数据。

## 4. 并发安全：为什么不会误删或留残

### 锁模型（锁序：gcMu → commitMu，永不反向）

- `gcMu sync.RWMutex`：
  - 所有内容读取/校验/提交持**读锁**（可大量并发）；
  - 回收 `Collect` 持**写锁**（与一切读/写互斥）。
  - 因此 GC 不可能在一次读取或一次内容提交的中途删除文件。
- `commitMu sync.Mutex`：串行化文件结构变更（去重提交、删除、隔离、用量记账、引用写）。
- 慢网络获取发生在 gcMu 之外，慢对端不会长时间阻塞回收。

### “获取 → 引用”无回收窗口

`Pin` 调用内部的受保护获取：内容“装配完成并通过复核”与“引用文件原子落盘”
在**同一个 gcMu 读锁临界区**内执行。GC 只可能观察到两种稳定状态之一：

- 引用尚不存在（此时 GC 也无法在临界区中途插入）；或
- 引用已经存在（内容受引用保护）。

引用文件自身也通过 `tmp + rename` 原子发布。

### 内容提交的不变量

远程补齐时，所有网络获取在锁外完成；随后在一个读锁临界区内
按“先全部分块、最后清单”提交。于是磁盘恒满足：

> **清单可见 ⇒ 该清单引用的全部分块已就位且哈希正确。**

GC 据此做引用计数与一致性补扫，不会留下“清单在但分块缺失”的不可读残留；
即使外部异常导致分块缺失，一致性补扫也会隔离该清单，使下次访问整体重新获取。

## 5. 回收后的再次访问

被回收的只是本地副本（对端/被 pin 的来源仍可保留）。再次 `Get/Pin` 时：

- 清单或分块缺失 ⇒ 自动从配置的对端重新获取；
- 重新获取的每个字节都重新哈希校验后才提交、才返回；
- 因此“回收后访问”得到的要么是经过完整验证的正确内容，
  要么是明确的 `not_found/missing/corrupt/capacity`，绝不会是损坏数据。

## 6. GC 报告

`Collect` 返回 `GCReport`：

```go
type GCReport struct {
    EvictedManifests  int   // 被驱逐的无引用内容数
    RemovedChunks     int   // 引用计数归零删除的分块数
    OrphanChunks      int   // 游离分块清理数
    StageTmpFiles     int   // 清理的崩溃残留临时文件数
    Quarantined       int   // 隔离的损坏/未知文件数
    ExpiredQuarantine int   // 过期删除的隔离文件数
    ReclaimedBytes    int64
    UsageBefore, UsageAfter int64
}
```
